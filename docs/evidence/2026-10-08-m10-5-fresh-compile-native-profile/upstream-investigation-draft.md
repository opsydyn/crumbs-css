# Draft: investigating fresh-build scan latency with the Vanilla Extract file-scope plugin

Local draft only. No issue has been posted and no upstream regression has been demonstrated.

We use `@vanilla-extract/integration` 8.0.10 with esbuild 0.27.7 to compile React Native style-authoring modules. We need fresh source/resolution/diagnostic behaviour on every call; a retained esbuild context or unproved compiled-text replay does not meet our current lifecycle/provenance requirements.

On macOS arm64 (M4 Pro, macOS 26.6.2), five fresh Bun 1.4.2 control processes compile two small graphs, each with nine bundled inputs and approximately 69 kB of transformed metafile input. The owned CJS diagnostic's integration wall medians are 5.937292 ms and 5.045958 ms after two setup transforms. An instrumented cohort with native `--timing` and integration debug-ID timers has similar wall results, printing median scan phase 4 ms, entry-point stage 1 ms, dependency scan 2 ms and compile/link 0 ms at the timer's coarse resolution. JavaScript debug-ID spans measure approximately 0.763/1.039 ms inside the scan; CSS reads are approximately 0.046/0.078 ms. These spans are nested/parallel and are not exclusive CPU costs.

The default compile is a Node-platform bundle with metafile, no write, external Vanilla Extract packages and the integration's file-scope plugin. The full-transform diagnostic adds three on-end collectors (two existing Crumbs collectors plus an observer). We are looking for supported ways to reduce **fresh-build scan, resolution or plugin/IPC overhead** without hiding fresh errors, changing identifiers/output, dropping input receipts, caching evaluated modules or adding a lifecycle-owning compiler to the library.

The attached local `graph/` and `minimal-compile.cjs` reduce the source fixture to eleven bundled files plus package/tsconfig. With integration 8.0.10/esbuild 0.27.7 resolved from a dependency project, the script performs stock fresh builds without Crumbs evaluation or its collectors. Smoke checks under Bun 1.4.2, Node 22.0.0 and Node 24.15.0 match the larger diagnostic's compiled source hashes and all nine inputs for each fixture. Those smoke checks are not timing comparisons. No npm installation or new package version is part of this packet.

Please help identify whether the scan latency is expected for this graph/plugin boundary, and whether a bounded stateless change can reduce it. In particular, we would value attribution separating native resolution/loading from waits on JavaScript callbacks and transport. A successful proposal must survive independent fresh output/input/diagnostic comparisons; our full warm-transform budget is 6.514 ms with a 15% relative ceiling, and our retained official result is 10.1715 ms. Improving an internal phase alone is not full admission.

We do not claim a production fix, a regression in esbuild, a native/device performance result, an exact Node-vs-Bun performance comparison or a lower bound on all possible adapters. The hidden native timer is undocumented, logging/instrumentation perturb execution, filesystem caches are uncontrolled and the isolated root differs from the official source-import workload. A one-process `GOMAXPROCS=1` pilot was slower; it is not a thread-tuning cohort. Public API changes, new dependencies, weak invalidation shortcuts and threshold changes are outside our current scope.
