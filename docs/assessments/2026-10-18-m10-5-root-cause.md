## What the new probes rule out

A fresh-read esbuild context avoids file-mtime reuse for the observed modules; adding a file-scope text memo avoids repeated Babel work. Stable fixture output hashes match, but observed full transforms still take roughly 8–10 ms in the exploratory runs. Their partial identities omit options/configuration/lifetime proof. They are not a production candidate. Limiting Go concurrency to one worsened compilation in its exploratory sample; changing JavaScript runtime or unrestricted exploratory execution did not eliminate the gap. None warrants adoption.

The stronger opportunity is **compiled JavaScript text reuse with fresh execution**, not cached evaluated exports or completed native styles. The corrected diagnostic requires two agreeing fresh compile results before readiness, checks every observed bundled input's bytes/canonical path on a hit, and retains the existing shipping checks around compilation. It then evaluates a new VM, captures styles and emits the complete module on every call.

## A negative control prevents a false victory

The envelope detects same-size/same-mtime edits and restoration of an already observed dependency. It nevertheless returns stale width11 when a new higher-priority `probe-input.ts` appears beside the unchanged `probe-input.js`; the fresh control returns width22. The existing shipping authoring receipts alone do not close that hole when a cached compile replays old inputs. Both stages and exact outputs are retained. **This failed candidate stays out of production.**

A complete witness must include every bundled input and relevant package/config/lockfile, unresolved/higher-priority candidates, logical/canonical routes and directory creation/removal/retargeting. Unsupported syntax, loaders, plugins, resolution forms and oversized graphs must compile fresh. Directory witnesses can avoid whole-tree source scans, but their complete cost remains unmeasured in this current artifact.

## The separate contract obstacle

The [October 8 identity prerequisite](2026-10-08-m10-5-compiler-identity-prerequisite.md) already rejected a compiled-text memo for a different reason: cached results were required to reproduce failures of a newly invoked compiler even when an installed native executable changed underneath a running worker. The demonstrated `esbuild.stop()` counterexample invalidates the tested namespace/disk-hash guard. This investigation does not invalidate that result or claim a universal impossibility proof.

Ordinary content reuse can be fast; preserving arbitrary live compiler-service failure equivalence is a separate requirement. Continuing to conflate these has sent the work back toward repeated full compilation. The existing approved spec requires rejection if its identity premise fails, so its prerequisite cannot simply be marked passed.

**Proposed replacement contract — owner decision required:**

1. A compiler installation and its loaded compiler/plugin implementation are fixed for one Metro worker/tooling-process lifetime. Changing the compiler installation requires restarting that worker/process. Public APIs and generated runtime imports stay unchanged.
2. A cache hit may use previously validated compiled text without invoking a healthy native compiler service. It is not required to reproduce a service-start failure when no compilation is needed. This explicitly changes the earlier exact fresh-error-equivalence requirement; it is not a numerical exception.
3. User-authored source, bundled design-system dependencies, manifests, configuration, lockfiles and resolution topology remain mutable and fully witnessed. Their changes invalidate the memo. Authoring and ambient reads execute on every transform. Cached failures/exports/native results remain forbidden.
4. Any incomplete or unsupported witness takes the existing fresh path. First discovery requires fresh confirmation. Before/after consumption checks, concurrency, bounded retention and existing package-scope restart diagnostics stay part of the design.
5. Admission still requires the unchanged official warm/cold/incremental and other blocking gates, parity and all required runtime-isolation/consumer tests. The old exact v1.2.0 tarball cannot acquire an optimization retroactively; any implementation is a new source/artifact that needs its own qualification and release identity.

This is the recommended direction, **not an accepted specification or implementation permission**. The alternative is to preserve exact fresh-error equivalence and retain the release block; a complete owned-service origin/lifetime mechanism would then need its own justified design and measured cost. No new loader, backend, shared host authoring exports, runtime import, public flag, budget revision or release exception is selected here.
